# E2E Flows — 사용자 여정 흐름 테스트

> 실제 사용자 관점의 전체 여정(가입 → 핵심 기능 → 결과 확인)을 **프로덕션 환경에서 Playwright MCP로 실증**하고, 그 기획과 실행 기록을 재사용 가능한 형태로 보관하는 폴더.

## 다른 문서 폴더와의 구분

| 폴더 | 성격 | 예 |
|------|------|---|
| `docs/qa-inspection/` | **시점성 점검** — 특정 시점에 페이지·기능을 일괄 점검한 리포트 | 149페이지 HTTP/렌더 점검 |
| `docs/planning/` | **기획 검토** — 기능 추가 전 타당성·전략 문서 | 결제 환불 기획 |
| `docs/e2e-flows/` | **흐름 정의 + 반복 실행 기록** — 페르소나 기반 시나리오를 정의하고 실제 실행할 때마다 리포트 축적 | 원클릭 배포 2-케이스 |
| `e2e/` (코드) | **자동 회귀 테스트** — localhost 기준 Playwright spec (CI용) | landing.spec.ts |

## 폴더 구조

```
docs/e2e-flows/
├── README.md                      # 이 파일 — 방법론 + 실행 이력
├── _templates/
│   ├── scenario-template.md       # 시나리오 정의서 템플릿
│   └── run-report-template.md     # 실행 리포트 템플릿
└── YYYY-MM-DD-{flow-name}/        # 흐름별 폴더 (최초 정의 날짜)
    ├── scenario.md                # 시나리오 정의서 (페르소나·스텝·검증 매트릭스)
    ├── run-{case}.md              # 실행 리포트 (실행할 때마다 추가, 재실행 시 run-{case}-2.md)
    └── screenshots/{case}/        # NN-step-name.png 순번 명명
```

## 방법론 — Playwright MCP 프로덕션 흐름 테스트

### 원칙

1. **페르소나 기반**: 시나리오는 "어떤 사용자가, 어떤 사전 지식으로" 시작하는지부터 정의한다. 같은 기능도 페르소나에 따라 검증 포인트가 달라진다 (예: 초급자 = 안내 문구 품질, 숙련자 = 단축 경로 동작).
2. **사용자 개입 체크포인트(CP) 명시**: 자동화 불가 지점(이메일 확인, OAuth 로그인, captcha, 장시간 지연 판단)은 시나리오 상단에 CP 표로 미리 선언한다. 실행자는 CP에 도달하면 중단하고 사용자에게 핸드오프한다.
3. **자격증명 비기록**: 비밀번호·토큰·인증 코드는 대화/문서/스크린샷 어디에도 남기지 않는다. CP에서 사용자가 Playwright 브라우저 창에 **직접 입력**하는 방식을 기본으로 한다. 스크린샷은 자격증명 입력 화면을 피해 입력 전/후 시점에 촬영.
4. **장시간 대기는 지수 백오프**: 빌드·CDN 전파 등 수 분 단위 대기는 1분 → 2분 → 4분 → 8분 간격으로 상태를 확인하고, 각 확인 시점에 진행 상황을 기록한다. 흐름별 타임아웃 상한을 시나리오에 명시 (원클릭 배포는 15분).
5. **판정은 가능한 한 기계적으로**: 화면 눈대중 대신 `browser_network_request`로 HTTP 상태·응답 본문을 직접 확인한다. 수정 반영 검증은 **유니크 마커 문자열**(예: `E2E-B-1718169600`)을 입력하고 라이브 URL 본문에서 검색한다. CDN 캐시는 `?_t={timestamp}` 캐시버스팅으로 우회.
6. **스크린샷 = 증적**: 각 스텝의 검증 포인트가 보이는 시점에 `NN-step-name.png`로 촬영. 번호는 시나리오 스텝 테이블의 스크린샷 컬럼과 일치시킨다.
7. **결함은 기록만**: 테스트 중 발견한 버그·UX 문제는 리포트에 심각도(CRITICAL/WARNING/INFO)와 함께 기록한다. 수정은 별도 작업으로 분리 — 테스트 실행 중 코드를 고치지 않는다.
8. **산출 자원 목록화**: 테스트가 만든 실제 자원(repo, 배포 사이트, 계정, 프로젝트)은 리포트 하단에 URL과 함께 목록화한다 — 이후 정리(삭제)의 근거.

### 세션 관리 (Playwright MCP는 persistent 프로필)

- 케이스 간 **세션 오염 주의**: 신규 사용자 케이스 전에는 대상 서비스 + OAuth 제공자(github.com 등) **모두** 로그아웃을 명시적 스텝으로 수행.
- 숙련자(기존 세션) 케이스 → 신규 케이스 순서로 실행하면 "로그아웃 → 클린 시작"이 자연스럽다.

### 주요 Playwright MCP 도구

| 도구 | 용도 |
|------|------|
| `browser_navigate` / `browser_snapshot` | 이동 + 접근성 트리 확인 (스텝 판정의 기본) |
| `browser_click` / `browser_type` / `browser_fill_form` | 인터랙션 |
| `browser_take_screenshot` | 증적 캡처 (`screenshots/{case}/NN-*.png`) |
| `browser_network_request` | HTTP 상태·본문 직접 확인 (마커 검색) |
| `browser_console_messages` | 콘솔 에러 0 검증 |
| `browser_wait_for` | 짧은 대기 (수 초). 분 단위 대기는 백오프 루프로 |

## 새 흐름 테스트 추가 절차

1. `_templates/scenario-template.md`를 복사해 `YYYY-MM-DD-{flow-name}/scenario.md` 생성
2. 페르소나·CP·스텝·검증 매트릭스 작성 (스텝의 "예상 결과"는 반드시 코드 근거와 함께 — 추측 금지)
3. 실행: 케이스별로 `_templates/run-report-template.md` 복사 → 진행하며 기입
4. 완료 후 아래 실행 이력 테이블에 한 줄 추가
5. P0/P1급 발견사항은 `docs/log/YYYY-MM.md`에도 기록
