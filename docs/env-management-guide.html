1 비유로 이해하기

열쇠 보관함 비유

환경변수 시스템을 "스마트 열쇠 보관함"에 비유하면 직관적으로 이해할 수 있습니다.

🔐
환경변수 = 출입카드
각 외부 서비스(Stripe, Supabase, OpenAI 등)에 접근하기 위한 인증 키입니다. 카드 없이는 서비스를 이용할 수 없습니다.
🏢
환경 (dev/staging/prod) = 건물의 층
같은 서비스라도 개발/스테이징/프로덕션 환경마다 다른 키를 사용합니다. 1층 출입카드로 3층에 들어갈 수 없듯이, dev 키로 prod에 접근하면 안 됩니다.
🎭
is_secret = 마스킹 여부
민감한 키는 ••••••••로 가려져 표시됩니다. 눈 아이콘을 클릭하면 5초간만 확인 가능합니다.
스마트 택배 분류기 비유

서비스 자동 매칭 시스템은 "스마트 택배 분류기"와 같습니다.

📦
Exact 매칭 = QR 코드 인식
STRIPE_SECRET_KEY는 Stripe 서비스의 required_env_vars에 정확히 등록되어 있으므로, QR코드를 찍듯 즉시 올바른 서비스 박스에 분류됩니다. 정확도 100%.
🏷️
Prefix 매칭 = 택배사 로고 인식
NEXT_PUBLIC_SUPABASE_ANON_KEY는 정확히 등록되진 않았지만, "SUPABASE" 접두사를 통해 Supabase 서비스로 유추합니다. 택배 상자의 기업 로고를 보고 분류하는 것과 같습니다.
✋
수동 연결 = 사람이 확인
DATABASE_URL처럼 어떤 서비스인지 특정할 수 없는 변수는 사용자가 직접 서비스를 지정해야 합니다.

2 12가지 기능 전체 맵

+
단일 추가
키 이름, 값, 환경, 비밀 여부를 지정하여 하나씩 추가합니다. 붙여넣기 시 서비스 자동 감지.
환경변수 페이지 POST /api/env
↑
벌크 가져오기
.env 파일 내용을 붙여넣으면 KEY=VALUE를 파싱하고, 프로젝트에 연결된 서비스를 자동 매칭합니다.
Import 다이얼로그 POST /api/env/bulk
✨
스마트 분석기
AI가 키 이름을 분석하여 서비스 매칭, 보안 등급, 설명을 자동 생성합니다. 3단계 위저드.
Analyzer 다이얼로그 POST /api/analyze/keys
↺
서비스 동기화
서비스 미연결 변수를 자동 매칭하고, 누락된 project_services를 생성하며, 연결 상태를 갱신합니다.
통계 헤더 Sync POST /api/env/sync
☰
환경별 관리
development, staging, production 3개 환경을 탭으로 전환하며, 환경별 변수 개수를 뱃지로 표시합니다.
필터 바 env-filter-bar.tsx
🔒
AES-256-GCM 암호화
모든 값은 서버에서 AES-256-GCM으로 암호화 후 DB 저장. IV + AuthTag + 암호문 형태로 저장됩니다.
서버 전용 src/lib/crypto/index.ts
⚠
충돌 검사
같은 키 이름이 여러 환경에서 다른 값을 가질 때 충돌을 감지합니다. 통계 카드에서 바로 접근 가능.
Conflicts 페이지 env-stats-header.tsx
↓
.env 다운로드
현재 환경의 변수들을 .env 형식으로 다운로드합니다. 서비스맵 사이드패널에서도 .env.local 다운로드 가능.
필터 바 Export GET /api/env/download
📂
GitHub Secrets 동기화
연결된 GitHub 레포에 환경변수를 Secrets로 자동 동기화. NaCl 암호화 후 GitHub API로 전송합니다.
Secrets Sync 패널 src/lib/github/auto-sync.ts
🤖
AI EnvDoctor
AI가 프로젝트의 환경변수 상태를 진단하고, 누락/중복/보안 이슈를 리포트합니다.
EnvDoctor 패널 AI Analyze API
🗑
소프트 삭제
삭제 시 deleted_at 타임스탬프만 설정하여 복구 가능. 실제 데이터는 DB에 유지됩니다.
DELETE API DELETE /api/env
🗺
서비스맵 사이드패널
서비스맵에서 서비스 노드 클릭 시 해당 서비스의 환경변수를 인라인으로 관리. Raw 에디터, 벌크 저장 지원.
서비스맵 패널 service-env-vars-section.tsx

3 사용자 여정

방법 선택 플로차트

환경변수를 추가할 때, 상황에 따라 최적의 방법이 다릅니다.

변수를 추가하려면?
        │
        ├── 변수가 1~2개인가? ──── YES ──── 방법 1: 단일 추가
        │                                         키 이름 + 값 입력
        │                                         서비스 자동 감지
        │
        ├── .env 파일이 있는가? ── YES ──── 방법 2: 벌크 가져오기
        │                                         .env 내용 붙여넣기
        │                                         일괄 파싱 + 서비스 매칭
        │
        └── 서비스 매칭 + AI 분석이
            필요한가? ──────────── YES ──── 방법 3: 스마트 분석기
                                              AI가 키 분석 + 서비스 매칭
                                              3단계 위저드로 검토 후 적용
방법 1: 단일 추가 (5단계)
1
환경변수 페이지 접속
프로젝트 > 환경변수 탭으로 이동합니다. /project/[id]/env
2
"추가" 버튼 클릭
필터 바 우측의 + 버튼을 클릭하면 추가 다이얼로그가 열립니다.
3
키 이름 입력
STRIPE_SECRET_KEY 같은 키를 입력합니다. 값을 붙여넣으면 서비스가 자동 감지됩니다. 여러 줄을 붙여넣으면 자동으로 Import 다이얼로그로 전환됩니다.
4
값, 환경, 설정 입력
값, 대상 환경(dev/staging/prod), is_secret 토글, 서비스 연결, 설명(선택)을 설정합니다.
5
저장
값은 AES-256-GCM으로 암호화되어 DB에 저장되고, GitHub Secrets 동기화가 트리거됩니다. 쿼터 초과 시 402 에러가 반환됩니다.
방법 2: 벌크 가져오기 (4단계)
1
Import 다이얼로그 열기
필터 바의 Import 아이콘 클릭, 또는 단일 추가 시 여러 줄 붙여넣기로 자동 전환됩니다.
2
.env 내용 붙여넣기
KEY=VALUE 형식을 파싱합니다. # 주석과 빈 줄은 자동으로 무시됩니다.
3
서비스 매칭 + 미리보기
각 변수에 대해 프로젝트에 연결된 서비스 중 매칭되는 것을 자동 연결합니다. Secret/Public 뱃지와 서비스명이 미리보기에 표시됩니다. NEXT_PUBLIC_ 접두사가 없으면 자동으로 is_secret=true.
4
일괄 생성
POST /api/env/bulk로 한 번에 생성됩니다. 감사 로그에 key_names와 count가 기록됩니다.
주의 (P0 버그): 벌크 가져오기 API에는 쿼터 체크가 누락되어 있습니다. Free 플랜(20개 제한)에서도 무제한 생성이 가능한 상태입니다. src/app/api/env/bulk/route.ts에 checkEnvVarQuota() 호출 추가가 필요합니다.
방법 3: 스마트 분석기 (5단계)
1
분석기 열기
필터 바의 분석 아이콘(sparkles)을 클릭합니다.
2
입력 (Step 1: Input)
단일 키 값 또는 .env 형식의 텍스트를 입력합니다. 줄바꿈이나 =이 없으면 단일 값으로, 있으면 멀티 키로 분석합니다.
3
AI 분석 (API 호출)
POST /api/analyze/keys로 AI가 각 키의 서비스 매칭, 보안 등급(high/medium/low), 자동 설명을 생성합니다.
4
검토 (Step 2: Review)
분석 결과를 검토합니다. 각 항목의 체크박스(제외 가능), 키 이름 편집, 서비스 변경, 대상 환경 선택이 가능합니다. 덮어쓰기 경고도 표시됩니다.
5
적용 (Step 3: Done)
POST /api/analyze/apply로 선택된 항목만 적용됩니다. 생성/업데이트/서비스 연결 수가 요약됩니다.
3가지 방법 비교표
항목 단일 추가 벌크 가져오기 스마트 분석기
최적 상황 1~2개 변수 빠르게 추가 .env 파일에서 복사 서비스 매칭 + AI 분석 필요
소요 시간 ~30초 ~1분 ~2분
서비스 매칭 붙여넣기 시 자동 감지 프로젝트 서비스 한정 AI 기반 전체 카탈로그 매칭
쿼터 체크 있음 누락 (P0) 있음
권장 환경 모든 환경 초기 셋업, dev 환경 새 프로젝트, 키 정리 필요 시

4 환경별 관리 전략

DEV
Development
실험과 개발을 위한 환경

목적: 로컬 개발, 기능 테스트

예시 값:

STRIPE_SECRET_KEY=sk_test_...
SUPABASE_URL=http://localhost:54321
NODE_ENV=development
권장: 테스트 키 사용, 자유롭게 변경 가능. 실제 결제 키 사용 금지.
STG
Staging
프로덕션 전 검증 환경

목적: 배포 전 통합 테스트, QA

예시 값:

STRIPE_SECRET_KEY=sk_test_staging_...
SUPABASE_URL=https://staging.supabase.co
NODE_ENV=production
권장: prod와 동일한 구조, 별도 테스트 계정. 변경 시 팀 공유 필수.
PROD
Production
실제 서비스 운영 환경

목적: 실제 사용자 서비스

예시 값:

STRIPE_SECRET_KEY=sk_live_...
SUPABASE_URL=https://prod.supabase.co
NODE_ENV=production
권장: 최소 권한, 변경 이력 필수 확인, 감사 로그 활성화. 실수 방지를 위해 별도 검토 프로세스.
환경 간 값 전파 워크플로우

새로운 환경변수를 안전하게 모든 환경에 배포하는 권장 순서입니다.

Step 1: Development에서 검증
새 키를 dev 환경에 추가하고 로컬에서 정상 동작을 확인합니다.
Step 2: 충돌 페이지 확인
/project/[id]/env/conflicts에서 다른 환경과의 키 충돌이 없는지 확인합니다.
Step 3: Staging에 복사
환경을 staging으로 전환하고, 같은 키를 staging 전용 값으로 추가합니다.
Step 4: Staging에서 테스트
staging 환경에서 통합 테스트를 수행합니다.
Step 5: Production에 배포
검증 완료 후 production 환경에 실제 값을 추가합니다. 감사 로그가 자동 기록됩니다.
Step 6: GitHub Secrets 동기화 확인
auto-sync가 활성화된 레포에 Secrets가 정상 반영되었는지 확인합니다.
GitHub Secrets 연동 설정법
1
GitHub 계정 연결
설정 > 서비스 계정에서 GitHub OAuth를 통해 계정을 연결합니다.
2
레포지토리 연결
프로젝트 설정에서 GitHub 레포를 연결합니다. project_github_repos 테이블에 저장됩니다.
3
Auto Sync 활성화
레포 설정에서 auto_sync_enabled=true와 동기화 대상 환경(sync_environment)을 설정합니다.
4
자동 동기화 발동
환경변수 CRUD(생성/수정/삭제) 시 triggerAutoSync()가 비동기로 호출됩니다. 각 변수는 NaCl로 재암호화 후 GitHub API를 통해 Secrets에 저장됩니다.
5
동기화 상태 확인
last_synced_at 타임스탬프와 감사 로그(github.auto_sync)에서 동기화 결과를 확인합니다. 개별 시크릿 실패 시에도 나머지는 계속 진행됩니다.

5 서비스 자동 매칭 원리

환경변수의 키 이름으로 어떤 외부 서비스에 속하는지 자동으로 판별합니다. src/lib/utils/env-service-matcher.ts에 구현되어 있습니다.

매칭 알고리즘 다이어그램
입력: NEXT_PUBLIC_SUPABASE_ANON_KEY
           │
           ▼
  ┌──────────────────────┐
  │  1. Exact Match       │   카탈로그 서비스의 required_env_vars[].name
  │  buildEnvKeyServiceMap │   과 1:1 대조
  └──────────┬───────────┘
             │ 매칭 실패
             ▼
  ┌──────────────────────┐
  │  2. 프레임워크 접두사  │   NEXT_PUBLIC_ / REACT_APP_ / VITE_ / NUXT_PUBLIC_
  │     제거              │   제거 후 → SUPABASE_ANON_KEY
  └──────────┬───────────┘
             │
             ▼
  ┌──────────────────────┐
  │  3. Prefix Match     │   첫 번째 세그먼트 추출 → "SUPABASE"
  │  buildEnvPrefixServiceMap│   접두사 맵에서 조회
  └──────────┬───────────┘
             │
        ┌────┴────┐
        ▼         ▼
  매칭 성공     매칭 실패
  confidence:   → null 반환
  'exact'/'prefix'  → 수동 연결 필요
매칭 정확도 비교표
키 이름 매칭 결과 confidence 설명
STRIPE_SECRET_KEY Stripe exact Stripe 서비스의 required_env_vars에 정확히 등록
NEXT_PUBLIC_SUPABASE_ANON_KEY Supabase prefix NEXT_PUBLIC_ 제거 후 "SUPABASE" 접두사로 매칭
OPENAI_API_KEY OpenAI exact OpenAI 서비스의 required_env_vars에 등록
VITE_FIREBASE_API_KEY Firebase prefix VITE_ 제거 후 "FIREBASE" 접두사로 매칭
DATABASE_URL 미매칭 - 범용 키 이름으로 특정 서비스 유추 불가
매칭 안될 때: 수동 연결 방법

자동 매칭에 실패한 변수는 두 가지 방법으로 수동 연결할 수 있습니다:

1
환경변수 페이지에서
변수 편집 다이얼로그 > 서비스 드롭다운에서 연결할 서비스를 선택합니다. 프로젝트에 연결된 서비스 목록이 표시됩니다.
2
동기화 기능으로
통계 헤더의 "동기화" 버튼을 클릭하면 POST /api/env/sync가 미연결 변수를 재분석하여 매칭을 시도합니다. 새 서비스가 카탈로그에 추가된 경우 유용합니다.
매칭 개선 팁: 환경변수 키 이름을 서비스명_기능_유형 패턴(예: STRIPE_WEBHOOK_SECRET)으로 작성하면 자동 매칭 성공률이 높아집니다. 프레임워크 접두사(NEXT_PUBLIC_ 등)는 자동으로 제거되므로 걱정하지 않아도 됩니다.

6 보안 관리

5단계 보안 레이어

환경변수는 입력부터 표시까지 5개의 보안 레이어를 거칩니다.

보안 아키텍처

Layer 1: 전송 암호화     HTTPS (TLS 1.3)
     │
     ▼
Layer 2: 입력 검증       Zod safeParse (key_name, value, environment)
     │
     ▼
Layer 3: 저장 암호화     AES-256-GCM
     │                     ┌─────────────────────────────────────┐
     │                     │  encrypt(plaintext)                 │
     │                     │  1. IV = randomBytes(16)            │
     │                     │  2. cipher = aes-256-gcm(key, IV)   │
     │                     │  3. encrypted = cipher.update(text)  │
     │                     │  4. authTag = cipher.getAuthTag()    │
     │                     │  5. DB 저장: iv:authTag:encrypted    │
     │                     └─────────────────────────────────────┘
     ▼
Layer 4: 접근 제어       RLS + API user_id 이중 방어
     │                     프로젝트 소유권 확인 (project.user_id = auth.uid)
     │
     ▼
Layer 5: 표시 보호       is_secret=true → ••••••••
                           복호화 클릭 시 서버 요청 → 5초 표시 후 재마스킹
                           복호화된 값은 로그/API 응답에 포함 금지
감사 로그

환경변수 관련 모든 민감 작업은 logAudit()를 통해 기록됩니다.

Action 트리거 기록 내용
env_var.create POST /api/env key_name, environment, service_id, is_secret
env_var.update PATCH /api/env 변경 필드 목록 (값 제외)
env_var.delete DELETE /api/env key_name (소프트 삭제)
env_var.bulk_create POST /api/env/bulk count, key_names, service_assignment_count

어떤 변수를 시크릿으로 표시해야 하는지 판단 기준입니다.

패턴 예시 is_secret 이유
NEXT_PUBLIC_* NEXT_PUBLIC_SUPABASE_URL false 클라이언트 노출 의도. 브라우저에서 접근 가능
*_KEY STRIPE_SECRET_KEY, OPENAI_API_KEY true 인증 키. 노출 시 과금/보안 사고 위험
*_SECRET WEBHOOK_SECRET, JWT_SECRET true 비밀 값. 노출 시 위변조 가능
*_URL DATABASE_URL, REDIS_URL true 연결 문자열에 비밀번호 포함 가능
*_TOKEN GITHUB_TOKEN, SLACK_TOKEN true 액세스 토큰. 노출 시 계정 탈취 위험
NODE_ENV NODE_ENV=production false 환경 식별용. 민감 정보 아님
*_PORT / *_HOST PORT=3000, API_HOST false 설정값. 보안 위험 낮음
현재 자동 감지 로직: 벌크 가져오기에서는 NEXT_PUBLIC_ 접두사가 없으면 무조건 is_secret=true로 설정합니다. NODE_ENV, PORT 같은 비민감 변수도 시크릿으로 표시되는 한계가 있습니다 (P3 개선 대상).

7 UX 문제점 & 개선 제안

P0 (즉시 수정)
P0-BUG
벌크 가져오기 쿼터 체크 누락
POST /api/env/bulk에 checkEnvVarQuota() 호출이 없어, Free 플랜(20개 제한)에서도 무제한 생성이 가능합니다.
수정: src/app/api/env/bulk/route.ts에서 소유권 확인 후 checkEnvVarQuota(userId, projectId)를 추가하고, current + variables.length > max이면 402 반환.
src/app/api/env/bulk/route.ts src/lib/quota.ts
P1 (1주 내 수정)
P1-1
deleted_at 필터 누락
환경변수 조회 시 deleted_at IS NOT NULL인 소프트 삭제된 항목이 목록에 계속 표시될 수 있습니다. 쿼리 훅에서 .is('deleted_at', null) 필터 확인 필요.
P1-2
값 복사 기능 부재
현재 "복사" 버튼은 키 이름만 복사합니다. 복호화된 값을 복사하는 기능이 없어 수동으로 눈 아이콘 > 텍스트 선택 > Ctrl+C 해야 합니다.
P1-3
environment 수정 불가
생성된 환경변수의 환경(dev/staging/prod)을 변경할 수 없습니다. PATCH API에는 environment 필드가 있지만, UI 편집 다이얼로그에서 환경 선택기가 비활성화되어 있습니다.
P1-4
아이콘 접근성 부족
필터 바의 아이콘 전용 버튼(분석, 가져오기, 내보내기)에 툴팁이나 aria-label이 부족하여 기능을 유추하기 어렵습니다.
P1-5
충돌 배지 미표시
통계 헤더의 "충돌 검사" 카드가 항상 동일하게 표시됩니다. 실제 충돌 개수를 계산하여 뱃지로 보여줘야 합니다.
P2 (1달 내 개선)
P2-1
환경 간 일괄 복사
dev의 변수를 staging이나 prod로 일괄 복사하는 기능이 없어, 환경 전환 후 하나씩 수동으로 추가해야 합니다.
P2-2
서비스명 검색
현재 검색은 키 이름 텍스트 매칭만 지원합니다. 서비스명(예: "Stripe")으로 해당 서비스의 모든 변수를 필터링하는 기능이 필요합니다.
P2-3
Optimistic Update
현재 CRUD 후 전체 목록을 refetch합니다. TanStack Query의 optimistic update를 적용하면 UX 응답성이 개선됩니다.
P3 (중장기)
P3-1
is_secret 자동 감지 개선
현재는 NEXT_PUBLIC_ 접두사 유무만으로 판단합니다. *_KEY, *_SECRET, *_TOKEN, *_URL 패턴과 NODE_ENV, PORT 등 비민감 변수를 화이트리스트로 관리하여 정확도를 높여야 합니다.
