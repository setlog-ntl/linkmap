1. 개념 이해하기 (초보자용)

Git Worktree = 같은 프로젝트의 "복사본 작업실"

당신이 레스토랑 주방장이라고 생각해보세요.

🍳

기존 방식

주방이 1개뿐입니다.
스테이크를 만들다가
파스타 주문이 들어오면
재료를 전부 치우고
파스타 재료를 꺼내야 합니다.

VS
🍳🍳🍳

Worktree 방식

주방을 3개 만듭니다.
주방 A: 스테이크 전담
주방 B: 파스타 전담
주방 C: 디저트 전담
동시에 요리, 서로 방해 없음

코드로 바꾸면: 주방 = 폴더, 재료 치우기 = git checkout (브랜치 전환), 여러 주방 = git worktree (독립 폴더)

실제로 뭐가 만들어지는가

C:/Dev/linkmap/ ← 원본 (main 브랜치) ├── src/ ← 소스 코드 ├── node_modules/ ← 원본의 라이브러리 (도구 세트) ├── package.json ← "어떤 도구가 필요한지" 적힌 목록 └── .git/ ← Git 저장소 (하나만 존재, 공유됨) C:/Dev/linkmap-wt-dashboard/ ← Worktree 1 (feat/dashboard 브랜치) ├── src/ ← 독립적으로 수정 가능한 코드 ├── node_modules/ ← 이 워크트리만의 라이브러리 └── package.json C:/Dev/linkmap-wt-auth/ ← Worktree 2 (fix/auth 브랜치) ├── src/ ← 또 다른 독립 코드 ├── node_modules/ ← 또 다른 독립 라이브러리 └── package.json
KEY 핵심: .git 폴더는 원본에 하나만 있고 워크트리들이 공유합니다. 통째로 git clone하는 것보다 훨씬 가볍습니다.

왜 워크트리마다 따로 설치하나요?

주방 A에서 "새 칼"(라이브러리)을 추가했는데,
주방 B에선 그 칼이 필요 없거나, 다른 버전이 필요할 수 있습니다.
→ 각자 독립적으로 관리해야 한쪽이 다른 쪽을 망가뜨리지 않습니다.

/wt-done                           # PR 만들고 → 테스트 통과하면 → main에 합치고
                                     # → 이 임시 폴더는 자동 삭제

자주 묻는 질문

Q: 원본 폴더(C:/Dev/linkmap)가 바뀌나요?

아닙니다. 원본은 main 브랜치 그대로 유지됩니다. 워크트리는 완전히 별도의 폴더입니다.

Q: 디스크를 많이 먹나요?

node_modules가 워크트리당 약 500MB~1GB입니다. 작업 끝나면 /wt-done이 자동으로 삭제합니다.

Q: 워크트리에서 만든 커밋은 어디에 저장되나요?

원본의 .git에 함께 저장됩니다. 워크트리 폴더를 삭제해도 커밋 기록은 사라지지 않습니다.

Q: 몇 개까지 만들 수 있나요?

제한 없습니다. 다만 디스크 공간을 고려하면 동시에 2~3개가 적당합니다.

Q: git clone과 뭐가 다른가요?

clone은 .git 저장소를 통째로 복사합니다 (수백MB 추가). Worktree는 .git을 공유하므로 소스 코드 + node_modules만 추가됩니다.

Q: 워크트리 A에서 만든 브랜치가 워크트리 B에서도 보이나요?

네. .git을 공유하므로 브랜치 목록은 모든 워크트리에서 동일합니다. 단, 같은 브랜치를 두 워크트리에서 동시에 체크아웃할 수는 없습니다.

4. 스킬 가이드

4개의 Claude Code 스킬로 전체 워크플로우를 커버합니다.

+
워크트리 생성
/wt-new <브랜치명> <설명>
CREATE

역할: 새 작업 환경을 독립된 디렉토리에 생성합니다. main 최신화 → 브랜치 생성 → 워크트리 생성 → npm install → 전환까지 자동 수행합니다.

1

2
브랜치 생성
3
Worktree 생성
4
npm install
5

# 설명만 입력 (브랜치명 자동 생성)

# 인자 없이 실행 (대화형으로 질문)
/wt-new

사용 예시

# 자동 메시지 생성
/gitp

# 메시지 직접 지정

✓
작업 완료 & 배포
/wt-done <PR 제목>

역할: 현재 워크트리의 작업을 완료합니다. PR 생성 → CI 통과 확인 → Squash Merge → 워크트리 정리까지 전체 프로세스를 자동화합니다.

1
상태 확인
2
Push & PR 생성
3
CI 모니터링
4
Squash Merge
5
정리 & 복귀

5단계 상세

단계동작실패 시
Phase 1 상태 확인 main worktree인지 확인, 미커밋 변경 확인 main이면 중단, 미커밋이면 /gitp 안내
Phase 2 PR 생성 git push → gh pr create --base main gh 미설치 시 설치 안내
Phase 3 CI 확인 지수 백오프로 CI 상태 모니터링 (1m → 2m → 4m) CI 실패 시 로그 표시, 수정 안내
Phase 4 머지 사용자 확인 후 gh pr merge --squash --delete-branch 사용자가 거부하면 중단
Phase 5 정리 main pull → worktree 제거 → main으로 복귀 -

/wt-done

# PR 제목 직접 지정

5. 실전 워크플로우

Claude Code 3개 세션 병렬 작업 시나리오

시간 세션 A (인증 수정) 세션 B (UI 개선) 세션 C (API 리팩토링) | | /wt-new fix/auth /wt-new feat/ui /wt-new refactor/api | linkmap-wt-auth/ 생성 linkmap-wt-ui/ 생성 linkmap-wt-api/ 생성 | | | | | 코드 수정... 코드 수정... 코드 수정... | /gitp /gitp /gitp | | | | | /wt-done | | | PR #101 생성 | | | CI 통과 | | | Squash Merge -----> 배포 #1 | | | wt-auth/ 제거 | | | /wt-done | | PR #102 생성 | | CI 통과 | | Squash Merge -----> 배포 #2 | | (A 변경 포함) | | wt-ui/ 제거 /wt-done | PR #103 생성 | CI 통과 | Squash Merge ----> 배포 #3 | (A+B 변경 포함) v wt-api/ 제거
POINT 핵심: 각 머지는 순차적으로 진행되므로, 이후 머지는 항상 이전 변경사항을 포함합니다. 동시 배포가 발생해도 concurrency 설정이 이전 배포를 자동 취소합니다.

7. CI/CD 변경사항

워크트리 워크플로우와 함께 CI/CD 파이프라인에 3가지 안전장치를 적용했습니다.

변경파일효과
Concurrency CI 중복 방지 ci.yml 같은 브랜치의 이전 CI 자동 취소
Concurrency 배포 중복 방지 deploy-cloudflare.yml 동시 배포 시 이전 배포 자동 취소
workflow_run CI 후 배포 deploy-cloudflare.yml CI 성공한 경우에만 배포 실행

배포 파이프라인 흐름

main에 머지
→
CI 실행
lint, test, build
→
CI 성공?
→
Cloudflare 배포
build:cf → wrangler deploy
BEFORE 
# deploy-cloudflare.yml
on:
  push:
    branches: [main]
# CI와 동시 실행, 실패해도 배포
AFTER 
# deploy-cloudflare.yml
on:
  workflow_run:
    workflows: ["CI"]
    types: [completed]
# CI 성공 후에만 배포

8. 규칙 & 주의사항

필수 규칙

규칙이유
main에 직접 push 금지CI 없이 배포되는 것 방지
항상 feature 브랜치에서 작업변경사항 누락 방지
Squash Merge 사용main 히스토리 깔끔하게 유지
머지 후 워크트리 & 브랜치 삭제디스크 & git 정리
Worktree 경로 규칙 준수C:/Dev/linkmap-wt-<name> 패턴

주의사항

  • npm install 필수: 각 워크트리는 독립된 node_modules가 필요합니다. /wt-new가 자동 처리합니다.
  • 동일 파일 수정 주의: 두 세션이 같은 파일을 수정하면 충돌이 발생합니다. 가능하면 파일 범위를 분리하세요.
  • 디스크 공간: 각 워크트리는 node_modules 포함 약 500MB~1GB를 차지합니다. 완료 후 반드시 정리하세요.
  • GitHub CLI 필요: /wt-done은 gh CLI가 필요합니다. winget install GitHub.cli → gh auth login
  • .git 공유: 워크트리들은 같은 .git을 공유합니다. 한 워크트리에서 생성한 브랜치는 다른 워크트리에서도 보입니다.

main 직접 push를 원천 차단하려면 GitHub에서 보호 규칙을 설정하세요.

Repository → Settings → Branches → Add rule

Branch name pattern: main

[x] Require a pull request before merging
    Require approvals: 0  (1인 개발 시)

[x] Require status checks to pass before merging
    [x] Require branches to be up to date
    Status check: "Lint, Type Check, Test, Build"
