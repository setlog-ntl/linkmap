- **카테고리:** #기능
- **중요도:** P1
- **지시:** "내 컴퓨터에 저장기능 추가해서 로컬에서 사용할 수 있게 업데이트"
- **맥락:** 이 템플릿의 핵심 약속이 "회사 파일이 밖으로 안 나간다"인데, 엑셀 엔진을 CDN에서
  받는 구조라 **CDN이 막힌 사내망에서는 도구가 아예 안 돌았다**(07-31 감사 P1). 019 영상은
  이미 오프라인 단일 HTML을 리드마그넷으로 쓰고 있어, 같은 것을 배포 산출물이 스스로 만들게 했다.
- **결과:**
  - `src/lib/standalone.ts`(신규 번들 파일) — 저장 시점에 SheetJS를 받아 HTML에 통째로 인라인한
    단일 파일을 생성. 도구 UI 상단에 "이 도구를 내 컴퓨터에 저장" 버튼 추가. 미리보기에도 반영.
  - 저장본은 **외부 요청 0건**(script/link/img src 전무, 내 코드 영역에 fetch·XHR·http 전무) —
    인터넷 없이, 외부 연결이 막힌 PC에서도 열린다. 취합 엔진은 온라인본과 동일 로직.
  - **함정 실측:** 처음엔 실제 함수를 `toString()`으로 직렬화해 심었는데 번들러 헬퍼(esbuild
    `__name`)가 딸려 나와 저장본이 `ReferenceError`로 즉사. `String.raw` 원문 문자열로 전환해 해결.
  - 검증: materialize→`tsc --noEmit` 통과(하네스 오탐 1건 제외, 미변경 템플릿도 동일) ·
    Playwright로 019 샘플 6종 실투입 → **52행·11열**, 「확인이 필요한 것」 4종 발화, 내려받은
    xlsx의 금액 52칸 전부 숫자(합계 813,069,100) — 019 문서의 정답과 일치. vitest 151/151.
- **인사이트:** 번들 파일 내용은 전부 문자열이라 linkmap의 tsc·eslint·vitest가 **전혀 검사하지
  않는다.** 게다가 템플릿은 eslint만 무시하고 타입 오류는 빌드를 깨므로, 번들 파일을 손대면
  materialize 후 별도 타입검사가 사실상 필수다(방법은 memory/oneclick-build-verification.md).

### 2026-08-01 — 로그인 전면 401 3차 재발 원인 확정: 잘린 GitHub Secret + 배포 게이트 봉인

- **지시:** "로그인오류 검토, 계속해서 오류발생하는데 원인분석·이유확인하고 이후에도

- **맥락:** 같은 날 새벽 레거시 anon 키 비활성화 사고, 저녁 "정상 판정" 이후에도 로그인

  이번엔 최신 배포 청크에서 발생 — 세션/구번들 문제가 아니었다.
- **결과:**

  - 정정: 13:10Z 배포도 오염(같은 잘린 Secret으로 빌드). 초기 "치유" 판정은 12:09Z 시절
    엣지 캐시/구버전 Worker 잔상을 최신 응답으로 오인한 것 — 크롬 실검증에서 `cache:no-store`

  - 실제 치유: Secret이 13:11~13:26Z 사이 정상값으로 재수정된 뒤, 검증 게이트를 통과한
    bc41913b 배포(13:26Z)가 정상 키 번들을 실어 해소. 크롬 실검증 — `/rest/v1/services` 200,
    `auth/v1/user` 200(세션 유지), 대시보드 풀 렌더, 콘솔 에러 0. /login → /dashboard
    자동 리다이렉트 복원(오염 번들에선 키 거부로 로그인 상태 인식 자체가 불가했음).
  - 재발 봉인(bc41913b): deploy-cloudflare.yml에 'Validate Supabase anon key' 게이트 추가
    — 형식(`sb_publishable_*` 접두사) + 라이브 수용(auth health 200) 검증 실패 시 빌드 전

### 2026-08-02 — 이틀간 로그인 장애 진범 확정: CF Workers Builds의 잘린 키 + 빌드 가드 봉인
- **카테고리:** #인프라 #버그
- **중요도:** P0
- **지시:** "계속해서 오류 발생, 원인 디테일하게 분석해서 문제없이 진행되도록 점검·해결"
- **맥락:** 08-01 "GitHub Secret 잘림" 결론(전날 로그) 이후에도 auth_exchange 로그인 실패와
  세션 사망이 반복. 크롬 검증에서 세션이 30분 내 반복적으로 죽는 것을 확인.
- **결과:**
  - 진범: **저장소에 연결된 Cloudflare Workers Builds**(CF 깃 연동 CI). 커밋 체크런
    "Workers Builds: linkmap"(Cloudflare Workers and Pages 앱)과 CF 감사로그의 고립
    배포가 매 push +3~4분에 정확히 일치. 그 빌드 변수에 앞글자 잘린 키(`b_publishable_…`)가
    저장되어 있어 **push마다 오염 빌드가 라이브를 덮어쓰고**, ~10분 뒤 GitHub Actions
    배포(게이트 통과)가 재치유하는 사이클이 이틀간 반복됐다.
  - 증거 사슬: Supabase api 로그 — 오염 창에서만 서버(UA null)발 `POST /token` ·
    `POST /visitor_logs` · `GET /user` 401("Invalid API key"), GoTrue auth 로그엔 /token
    부재(게이트웨이 거부 신호). Workers observability `[track] insert failed: Invalid API key`
    타임라인이 고립 배포 버전의 라이브 창(04:33·04:52 등)과 일치. CI 버전 라이브 창은 청정.
  - **전날 결론 정정**: GitHub Secret은 처음부터 정상(게이트 통과 이력 전부 성공).
    "Secret 잘림→재수정" 서사는 CF 빌드가 끼어드는 것을 몰라 생긴 오진. 13:00Z/13:10Z
    "오염 배포"도 실제로는 직후의 CF Workers Builds 배포였다.
  - 조치: ① next.config.ts에 **빌드 시 키 형식 가드** — `sb_publishable_` 아니면 어떤
    파이프라인이든 빌드 실패(오염 배포 원천 차단, placeholder-key 허용). push 즉시 CF
    오염 빌드도 이 가드로 실패하게 됨. ② 사용자 액션 필요: CF 대시보드에서 Workers Builds
    연결 해제(권장) 또는 빌드 변수 키 수정 — GitHub Actions가 유일 배포 경로가 되어야 함.
  - 부수 진단 확립: `content/v2?version=` API는 version 파라미터를 무시하고 최신 콘텐츠를
    반환함(버전 비교에 사용 금지). 커밋 체크런의 "Workers Builds:" 존재가 CF 빌드 연결의
    가장 빠른 판별법.
- **인사이트:** "배포 파이프라인이 두 개"인 순간 모든 배포-시점 검증은 무력화된다 —
  게이트는 자기 파이프라인만 지킨다. 검증은 파이프라인이 아니라 **빌드 자체**(next.config)에
  심어야 어떤 경로로 빌드해도 걸린다. 원인 불명의 "정상↔오염 핑퐁"은 복수 배포 주체를
  의심하라(CF 감사로그 script_update의 고립 이벤트 + 커밋 체크런으로 판별).
