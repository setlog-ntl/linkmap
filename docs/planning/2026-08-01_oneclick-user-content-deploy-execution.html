원클릭 “내 자료 배포” — 실행·검증 기록

템플릿이 아니라 사용자가 만든 자료와 사용자의 GitHub 저장소를 배포하는 두 트랙을 추가했다. AI가 만들어준 HTML은 손에 있는데 배포를 못 하던 사람이 퍼널 밖에 있었다.

01무엇을 만들었나

트랙 A — 내 파일 올리기 브라우저: 단일 HTML · ZIP · 폴더 │ 해제 · 정규화 · 첫 화면 판정 · 상한 검사 ← 전부 브라우저 (원본은 서버로 가지 않는다) ▼ POST /api/oneclick/deploy-upload { files[]: path · content · encoding } ▼ 저장소 생성 → Pages 활성화 → 원자 커밋 → 상태 폴링 트랙 B — 내 GitHub 가져오기 저장소 목록 → 분석(정적/빌드 · 권한 · Pages 상태) │ 동의 화면: 커밋될 YAML 전문 + 불변 보증 ▼ .github/workflows/linkmap-pages.yml 1개만 커밋 (기존 파일 무수정) ▼ Pages 활성화 → 상태 폴링

트랙 A — 내 파일 올리기

ZIP 해제를 서버가 아니라 브라우저에서 한다. Workers CPU 예산을 배포가 온전히 쓰고, zip bomb이 터져도 사용자 탭에서 끝나며, “업로드 원본을 보관하지 않는다”는 원칙이 구조적으로 보장된다 — 서버는 아카이브를 수신조차 하지 않는다.

트랙 B — 내 GitHub 가져오기

저장소는 사용자 자산이다. 그래서 기능보다 “무엇을 하지 않는가”를 먼저 고정했다. 워크플로우 파일 1개만 추가하고, 기존 파일을 수정하지 않으며, 저장소를 삭제하지 않는다.

02보안 경계는 셋으로 좁혔다

이 기능의 본질은 “사용자가 만든 임의의 HTML·JS를 사용자 본인 계정과 도메인에 게시”하는 것이다. index.html 자체가 임의 스크립트인데 일부만 검사하는 것은 의미가 없다. 그래서 콘텐츠는 검사하지 않고, 대신 “Linkmap 인프라와 다른 사용자에게 해가 되는가”만 막는다.

경계지키는 방법
워크플로우 인젝션 차단 사용자 .github/는 전량 드랍하고 서버 상수 워크플로우만 주입한다. 사용자 입력이 YAML에 보간되는 지점은 0이며, 경로·브랜치·빌드 명령은 화이트리스트를 통과해야 한다 — 이스케이프가 아니라 거부한다.
경로 무결성 상위 경로 참조·절대 경로·제어문자·숨김 파일을 거부한다. 편집 경로는 퍼센트 인코딩(%2Egithub/…)까지 디코딩한 뒤 검사한다.
파일 모드 고정 tree 항목을 전부 100644로 만든다. symlink·실행 파일은 코드 경로상 생성 자체가 불가능하다.

콘텐츠 자체의 적법성은 ToS와 GitHub AUP로 사용자 책임이다. 커밋은 사용자 본인 토큰으로, 본인 계정에 이뤄진다.

03진행 순서

0
보안 선결 + 공통 기반

OAuth 콜백이 state_token만으로 사용자를 식별하고 있었다. 공격자의 state로 피해자의 인가를 유도하면 피해자 토큰이 공격자 계정에 묶인다. 재현 테스트로 먼저 실증한 뒤 세션 대조를 넣었다. 이어서 oauth_states RLS가 user_id만 강제해 타인 project_id를 담은 state를 직접 만들 수 있던 문제(크로스테넌트 GitHub 연결 탈취)도 함께 막았다.

타 세션 state → 403 · 토큰 교환 미발생 · service_accounts 미변경
1A
트랙 A — 파일 업로드

단일 HTML·ZIP·폴더가 모두 하나의 파일 배열로 수렴하도록 만들어 서버 검증을 단일화했다. 래퍼 폴더 자동 벗기기, 첫 화면 판정, 상한(60개 · 25MB)까지 브라우저에서 끝낸다.

단일 HTML → 사이트 200 · .github/evil.yml 포함 ZIP → 커밋 트리에 부재 · 61개 파일 → 400
1B
트랙 B — 내 GitHub 저장소 연결

가장 먼저 한 일은 기능 추가가 아니라 삭제 가드였다. 기존 삭제 API가 GitHub 저장소를 지우고 있어서, 가져온 저장소에 그대로 적용됐다면 사용자의 원본이 사라진다. 재현 테스트로 위험을 실증한 뒤 막았다.

배포 후 트리 diff = 워크플로우 1개 추가뿐 · import 삭제 → 저장소 존재 유지
2
빌드형 프로젝트 지원

1B까지는 완성된 index.html이 저장소에 있어야 했다. 실제 프로젝트는 빌드 산출물을 저장소에 넣지 않는 것이 정상이라 이 제약은 대부분의 진짜 저장소를 막는다. 프레임워크를 감지해 빌드 워크플로우를 주입하도록 바꿨다.

프레임워크 감지 21건 · 셸 메타문자 포함 명령 거부 · 산출물 경로 화이트리스트

05검증 과정에서 찾아 고친 것

적대적 리뷰와 라이브 테스트에서 나온 결함들이다. 특히 아래 셋은 단위 테스트로는 잡히지 않는 종류였다 — 탭 전환, 미리보기와 실제의 괴리, 만료된 세션에서의 안내 문구.

심각도결함조치
치명 자동 재시도가 사용자의 deploy.yml을 실행 — 상태 판정이 워크플로우를 기본 인자로 dispatch했다. deploy.yml은 실사용 저장소에서 가장 흔한 이름이고 대개 프로덕션 배포를 수행한다. 게다가 상태 조회가 브랜치 main 고정·워크플로우 무필터라 남의 CI 실패를 우리 배포 실패로 오독해 트리거 조건까지 헐거웠다. 배포별로 워크플로우 파일·브랜치를 전달하고, 가져온 저장소는 자동 재시도를 금지
높음 사용자 원본 저장소 삭제 — 사이트 삭제가 GitHub 저장소를 함께 지웠다 source_type === 'import' 가드 + 재현 테스트
높음 워크플로우 인젝션 우회 — 편집 경로의 금지 패턴이 리터럴만 검사해 %2Egithub/workflows/x.yml이 통과했고, Contents API URL에서 GitHub이 디코딩하면 .github/로 복원됐다 검사 전에 (이중까지) 디코딩 · 회귀 테스트 7건
높음 편집기가 사용자 저장소를 덮어씀 — 파일 편집·일괄 수정·업로드 라우트가 source_type을 몰랐다 세 라우트 403 + 편집 진입 숨김
중간 배포 진행이 다른 탭으로 옮기면 멈춤 — “페이지를 닫지 마세요”라고 안내하는 화면인데 폴링이 중단됐다. 6분간 “설정 중”인 동안 사이트는 이미 떠 있었다 백그라운드에서도 폴링 유지
중간 미리보기가 실제와 불일치 — 차단 규칙이 서버에만 있어 요약 카드에 .github/evil.yml이 그대로 표시됐다. 보안 경계는 무사했지만 사용자에겐 본 파일이 조용히 사라지는 경험 클라이언트에도 같은 규칙 적용 + 제외 사유를 배포 전에 표시
중간 동의 화면과 실제 동작 불일치 — 폴더를 바꿔도 미리보기 YAML은 기본값 고정, 가장 결과가 큰 행위인 Pages 공개가 목록에 없었다 미리보기를 선택값으로 갱신 · 공개 사실과 URL을 최상단에 명시
높음 Vite 프로젝트가 빌드 없이 원본째 배포 — Vite·CRA는 저장소 루트에 index.html을 두는데 그건 완성된 페이지가 아니라 /src/main.js를 참조하는 빌드 입력 템플릿이다. “루트에 index.html이 있으면 정적”으로 판정해 빌드를 건너뛰었다 — 배포는 성공하고 화면만 비는 실패 판정을 순수 함수로 분리하고 게시 폴더 / 루트 템플릿 / 순수 정적을 구분

06빌드형 지원과 그 한계

프레임워크를 감지해 npm ci → npm run build → 산출물 업로드 워크플로우를 주입한다. 설정 파일은 읽지도 고치지도 않고, 저장소에 이미 있는 스크립트를 그대로 실행한다.

GitHub Pages는 /<저장소이름>/ 하위에 서비스한다. 우리는 사용자 설정 파일을 고치지 않으므로 고칠 수 없는 경우가 있고, 그때는 숨기지 않고 배포 전에 알린다.

주입이 없었다면 자산 경로가 /assets/…가 되어 하위 경로 배포에서 404가 났을 것이다. 이 검증이 --base 주입의 실효를 직접 확인한 지점이다.

빌드 명령에도 화이트리스트를 적용한다. &&·;·$()·| 같은 셸 메타문자가 있으면 이스케이프하지 않고 거부한다.

07데이터베이스 변경

마이그레이션 109 — user_source_deploys

  • template_id를 NULL 허용으로 바꾸고 source_type(template · upload · import)을 추가했다.
  • 정합성 제약: (source_type = 'template') = (template_id IS NOT NULL) — 가짜 템플릿 행으로 때우는 대신 DB가 직접 강제한다.
  • RPC는 기본값 인자로 인한 오버로드 모호성 때문에 DROP 후 7-인자로 재생성했다.

재생성 기준은 M101이었다. M100 기준으로 썼다면 trial 중인 Pro·Team 사용자가 무료 한도로 차단되는, 이미 고쳐진 사고가 재발했을 것이다 — 리뷰에서 잡아 적용 전에 정정했다.
