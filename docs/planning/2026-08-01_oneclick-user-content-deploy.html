원클릭 "내 자료 배포" — 파일 업로드 · 내 GitHub repo 자동 배포

템플릿이 아닌 사용자가 만든 자료(AI 생성 HTML/ZIP)와 기존 GitHub 저장소를 원클릭으로 배포 — 구현 착수 전 실행 설계 문서

1결론 요약

기술적으로 가능한가?

가능 — 배포 엔진(repo 생성→원자 push→Pages 활성화→폴링→쿼터→에러 분류→showcase)을 전면 재사용. 신규는 업로드 검증·repo 분석·스키마 확장뿐.

원클릭 컨셉과 충돌하는가?

아니오, 오히려 확장 — 템플릿 앞단에 새 진입로. 바이브코더 최빈 시나리오("AI가 준 파일이 손에 있다")가 퍼널 안으로.

가장 큰 위험은?

기존 repo 파손 — 현재 삭제 API가 GitHub repo를 삭제(deployments/[id]/route.ts:127). source_type 가드가 최우선 안전 요건.

선결 조건은?

P0 수정 — OAuth 콜백 크로스계정 CSRF(07-12 감사 미수정). 신규 트랙이 노출면을 확대하므로 출시 게이트.

핵심 원칙 — "서버는 원본을 만지지 않고(클라이언트 해제·즉시 폐기), 사용자 repo는 파일 1개 추가 외 절대 건드리지 않는다"

3트랙 A — 파일 업로드 설계

3.1 ZIP 해제 위치 — 클라이언트(브라우저) 확정 채택
  • Workers CPU(cpu_ms 30000) 영향 없음 — 해제·검증·인코딩 전부 브라우저 부담. zip bomb 폭발도 사용자 본인 브라우저에 국한
  • "원본 즉시 폐기"의 구조적 보장 — 서버가 ZIP을 수신조차 하지 않음. 서버 API는 항상 파일 배열 JSON만 수신 (단일 HTML/ZIP/폴더가 하나로 수렴 → 검증 코드 단일화)
  • fflate 1개 추가 (unzip 코어 ~8KB gz, 클라 번들 한정 dynamic import — 서버 번들 오염 금지 규칙 준수). 유틸: src/lib/oneclick/client-zip.ts
  • 정규화: __MACOSX/·.DS_Store·.git/ 폐기 → 단일 최상위 폴더 unwrap(AI 도구의 폴더째 압축 관행) → 확장자·경로 필터 → 텍스트/바이너리 판별·base64

3.3 보안 게이트 — upload-sanitizer.ts (서버, 전량 재검증)
  1. 경로 무결성: ..·선행 /·백슬래시·제어문자·256자 초과 거부. dot 파일은 조용히 드랍 + skipped_files[] 보고
  2. 심볼릭 링크 구조적 무해화: tree 모드 전부 100644 고정 — symlink(120000)·실행(100755) 생성 경로 자체가 없음
  3. .github/ 완전 차단 + 표준 워크플로우 주입: 사용자 .github/ 전량 드랍 후 Linkmap 표준 정적 deploy.yml만 주입 (static-workflow.ts 신규 — npm 없는 upload-pages-artifact 방식, 사용자 입력이 YAML에 보간되는 지점 0). 파일명 deploy.yml 유지 → 기존 redeploy·상태 추적 무수정 동작
  4. 확장자 허용 목록: 정적 자산 전반(html/css/js/json/md/svg/이미지/폰트/미디어/pdf). exe/sh/php 등 불허(드랍+보고) — 실행 불가라 실질 위험 낮지만 남용 인상·스캐너 오탐 감소
  5. 매직바이트는 이미지만 — HTML/JS 콘텐츠 검사는 하지 않음

책임 분계 원칙: 본질이 "사용자 임의 HTML을 사용자 본인 계정·도메인에 게시"이므로 콘텐츠 검사는 무의미. 경계선은 ① 워크플로우 인젝션 차단 ② 경로 무결성 ③ Linkmap 도메인 비렌더링. 콘텐츠 적법성은 ToS + GitHub AUP로 사용자 책임 (R1).

3.4 index.html 판정 6단계 (결정을 요구하지 않는다)

① 루트에 있음 → 통과→② 폴더 안 → 자동 unwrap→③ 단일 HTML 다른 이름 → 자동 rename+고지→④ ZIP 내 HTML 1개 → index.html 복제 추가(링크 보존)→⑤ 여러 개 → "첫 화면 고르기" 선택 UI→⑥ 0개 → 차단 + 바이브코더 눈높이 안내

3.5 미리보기 — Phase 1 제외, "파일 요약 카드"로 대체

  • Linkmap 도메인에서 임의 HTML 렌더링 = 유일한 자사 도메인 XSS 벡터 (site-editor iframe P1 선례) — 원천 제거
  • 다중 파일 사이트는 srcdoc에서 상대경로 자산이 깨져 깨진 미리보기 = 신뢰 하락. 사용자는 로컬에서 이미 봤고 배포는 무료·수 분·재시도 가능
  • 대체: 요약 카드(파일 수·용량·트리·"첫 화면"·드랍 목록) → 곧장 배포. Phase 2에서 단일 HTML 한정 sandbox 미리보기 재검토

4트랙 B — 내 GitHub repo 연결 설계

4.1 repo 선택 — 신규 GET /api/oneclick/repos
  • 기존 /api/github/repos는 project_id 필수·페이지네이션 없음 → 신설 (기존 라우트 무수정, 회귀 위험 0)
  • listUserRepos 확장: page/per_page(기본 30)/affiliation=owner (Pages 활성화 = admin 권한 필수 — collaborator는 Phase 1 제외) + has_next
  • 검색: 로드된 페이지 클라 필터 + "더 보기" (바이브코더 repo 수 대부분 <60 — Search API는 Phase 2 백로그)
4.2 repo 분석 — 신규 POST /api/oneclick/repo-analyze
  • getRepo: permissions.admin 필수 · fork/private/size/default_branch 확보
  • getGitTreeRecursive: 빈 repo → 차단+트랙 A 안내 / truncated(거대) → 정밀 분석 생략+경고 / size > 1GB → Pages 소프트 리밋 경고
  • 정적 판별: index.html을 / → docs/ → dist/ → build/ → public/ → out/ 순 탐색 = publish_dir 기본값. 미발견+package.json → 빌드형 판정(Phase 1 차단, "곧 지원됩니다" Phase 2 훅)
  • Pages 기존 상태: 자체 workflow 있으면 "연결만 하기(link-only)"(커밋 0) / legacy(브랜치 빌드)면 workflow 전환 고지(updatePagesBuildType 신규)
  • 워크플로우 파일명 항상 .github/workflows/linkmap-pages.yml — deploy.yml 충돌 원천 차단 + 소유권 자명 + 롤백 대상 명확. config_data.workflow_file 기록
  • fork → Actions 기본 비활성 → PUT .../actions/permissions 선행 + 고지 / private → GitHub Free는 Pages 불가 경고 + 전용 에러 매핑
4.3 동의 화면 — "무엇이 일어나는지" 전문(全文) 공개
  • 헤더: "owner/repo에 딱 1개의 파일을 추가합니다" + 접이식 YAML 전문 (추가 1·수정 0이므로 diff = 파일 전문)
  • 불변 보증 체크리스트: "기존 파일 무수정 / 저장소 삭제 안 함 / 커밋 메시지 명시"
  • 조건부 고지: legacy 전환 · fork Actions 활성화 · link-only("아무것도 커밋하지 않습니다")
  • CTA: "1개 파일 커밋하고 배포" — 행동 서술형 ('동의' 같은 추상 버튼 금지)

4.4 실패 롤백 — "우리가 만든 것만, 우리가 지운다"

5공통 설계

5.1 DB — 마이그레이션 109_user_source_deploys.sql
  • 채택: template_id nullable + source_type 컬럼 (CHECK: template/upload/import + 정합성 CHECK (source_type='template') = (template_id IS NOT NULL)). sentinel 템플릿 기각 — 카탈로그·showcase·통계 오염 + UI 분기 이중화
  • deploy_method='github_pages' 유지 — 호스팅 방식은 세 소스 모두 동일. 상태 추적·queries 리터럴 전부 무수정. 소스 구분은 source_type 전담
  • RPC 교체: p_source_type 추가 시 구 6-인자 함수와 오버로드 충돌 → DROP FUNCTION 후 재생성 + M108 정책대로 REVOKE FROM PUBLIC·GRANT TO authenticated 재적용, has_function_privilege 검증
  • config_data: A {file_count, total_bytes, skipped_files} / B {workflow_file, publish_dir, source_branch, pages_was_enabled, prior_build_type, link_only}. 유휴 컬럼 project_github_repos.sync_branch/sync_directory 재활용
  • 마이그레이션 후 3-step: types 동기화 → queries 반영 → db-schema.md 갱신
5.2 API 4종 (5단계 패턴 준수)
  • POST /api/oneclick/deploy-upload — 기존 deploy 골격 복제 + sanitizer + 워크플로우 주입 + RPC(source_type='upload')
  • POST /api/oneclick/deploy-repo — 서버에서 분석 재실행(클라 결과 신뢰 금지) → 1파일 커밋 → Pages → RPC(source_type='import'). 실패 시 repo 삭제 절대 금지
  • GET /api/oneclick/repos · POST /api/oneclick/repo-analyze — §4.1/4.2
  • Zod 스키마 4종 (validations/oneclick.ts) · 에러 카테고리 2종 추가(upload_validation·repo_not_deployable) — 서버·클라·DB 3곳 동기화
5.3 위저드 — phase 무변경, payload 일반화
  • DeploySource 판별 유니온 (template/upload/import) — deploying에서 kind별 mutation 3종 분기
  • OAuth 리다이렉트 제약: 파일 payload는 localStorage에 못 넣음 → 업로드/임포트 트랙은 인증 완료 후 입력 진입 (템플릿 트랙의 선입력·후인증 순서를 이 두 트랙만 역전). pending에는 track 표식만 저장
  • 클라 전처리(해제·정규화·index 판정)는 selecting 내부 컴포넌트 로컬 상태 — 머신 단순성 유지
5.4 my-sites 통합 · 5.5 2층 퍼널 브릿지
  • 소스 뱃지 3종(템플릿명/내 파일/내 repo) + template null 시 generic 프리뷰 fallback
  • 모듈 패널은 source_type==='template'만 렌더. upload는 파일 에디터 허용(무수정 동작), import는 Phase 1 에디터 비활성("GitHub에서 편집" 링크)
  • 재배포: import는 config_data.workflow_file·sync_branch를 workflow dispatch에 전달
  • 멀티계정 P1(첫 active 계정 토큰 오참조)이 import private repo에서 표면화 → 1B에서 project_github_repos.service_account_id 우선 해석으로 부분 수정
  • 2층 브릿지 = 추가 작업 0: 기존 파이프라인 재사용으로 projects+서비스맵 GitHub 노드 자동 생성. Phase 3: 업로드 HTML SDK 시그니처 스캔 → 서비스맵 자동 제안 (바이브코더→관리자 전환 이벤트)
