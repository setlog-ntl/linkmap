환경변수 중계(Relay) API 서비스 고도화

기획 검토일: 2026-03-22 | 프로젝트: Linkmap | 상태: 기각

1. 기능 개요

사용자가 Linkmap에 등록한 환경변수(OpenAI, Stripe, Supabase 등의 API 키)를 외부 런타임 환경에서 Linkmap API 토큰 하나로 pull할 수 있는 중계 서비스.

"Linkmap 키 하나만 연결하면 모든 서비스가 자동 연결"되는 경험 제공.

구상 동작 흐름

사용자 ─── [1] API 키 등록 ───> Linkmap DB (AES-256-GCM 암호화) | [2] 토큰 발급 (stl_xxxx) | 외부 서비스 <── [3] LINKMAP_TOKEN ──── | (Vercel, Railway) | | | └── [4] SDK/CLI fetch ──────> 복호화 & 반환 | [5] 감사 로그 기록

3-2. 기술 아키텍트 관점 2/5

(1) 단일 ENCRYPTION_KEY 문제 (CRITICAL)

현재: 모든 사용자의 환경변수가 하나의 ENCRYPTION_KEY로 암호화
문제: 이 키가 유출되면 전체 사용자의 모든 환경변수가 노출

경쟁사 비교:
  Doppler   → 테넌트별 키
  Infisical → E2EE (사용자 키쌍)
  Vault     → per-path 암호화

src/lib/crypto/index.ts의 getKey()가 process.env.ENCRYPTION_KEY 하나만 사용. 중계 서비스 전환 시 per-user 또는 per-project 암호화가 필수이며, 이는 기존 데이터 전체 마이그레이션 + 암호화 아키텍처 재설계를 의미.

(2) Cloudflare Workers 제약

  • CPU 시간 제한: Free Plan 10ms, Paid 30ms
  • 환경변수 bulk 복호화는 CPU 집약적 (수십~수백 개 AES-256-GCM)
  • Workers KV/Durable Objects 없이 세션/캐싱 어려움
  • WebSocket 미지원 (실시간 변경 감지 불가)

(3) 토큰 스코프 부재

  • 현재 api_tokens에 스코프/권한 필드 없음
  • 토큰 하나로 해당 사용자의 모든 프로젝트, 모든 환경변수 접근 가능
  • 최소 project-scoped + environment-scoped 토큰 필요

(4) 가용성 보장 불가

  • 현재 Cloudflare Workers Free Plan 사용 (SLA 없음)
  • 503 에러 이력 존재
  • 중계 서비스는 외부 앱 부팅에 직접 영향 → 99.9%+ 가용성 필수

(5) 예상 변경 범위

영역변경 내용
암호화src/lib/crypto/index.ts — per-project 키 파생 로직 추가
토큰src/app/api/tokens/route.ts — 스코프 기반 토큰 생성
새 APIsrc/app/api/relay/ — 환경변수 중계 전용 라우트
DB새 테이블 3~5개: token_scopes, relay_access_logs, ip_allowlist
SDKpackages/sdk-node/, packages/sdk-python/
마이그레이션3~5개 이상

3-3. UX 디자이너 관점 3/5

긍정적

  • "하나의 키로 모든 것 관리" 메시지는 강력

  • 대시보드에서 키 사용처 시각화 가능

부정적

  • 토큰 스코프, IP 화이트리스트 등 새 UI 대량 필요

4. 기각 핵심 근거 (3가지)

  1. 보안 아키텍처 근본 미달 — 단일 ENCRYPTION_KEY, 토큰 스코프 없음, MFA 없음, 키 로테이션 미수립. 시크릿 중계 서비스의 최소 보안 요건(SOC 2 수준)에 현저히 미달. 이 상태에서 "다른 서비스의 키를 관리하는 서비스"를 운영하는 것은 사용자에게 거짓 안전감을 주는 위험한 행위.
  2. 타겟 사용자 불일치 — 바이브코더(코딩 경험 0)에게 SDK 설치 + 토큰 관리 + fetch 코드 작성을 요구하는 것은 "원클릭 배포"라는 핵심 가치와 정면 충돌. 실제로 .env 직접 복붙보다 단계가 늘어남.
  3. 경쟁 우위 부재 — Doppler(40+ 통합, Free/3명), Infisical(오픈소스, E2EE), Vault(엔터프라이즈 표준)에 비해 차별화 요소 없음. 이들을 이기려면 SOC 2 인증, 수십 개 통합, 보안 감사 등 막대한 투자 필요.

5. 채택된 방향: 자동 동기화 (Push)

추진 결정 2026-03-22

중계(Pull) 대신 Push 방식 채택 — Linkmap에서 환경변수 변경 시 Vercel/Railway/Netlify에 자동 반영. SDK 불필요, 버튼만 클릭.

핵심 발견: GitHub Secrets 자동 동기화가 이미 완전 구현

기존 구현파일상태
자동 동기화 트리거src/lib/github/auto-sync.ts179줄 완전 구현
환경변수 CUD 시 트리거src/app/api/env/route.ts (3곳)구현됨
NaCl 암호화 + API Pushsrc/lib/github/nacl-encrypt.ts구현됨
동기화 상태 DBproject_github_repos구현됨
UI 패널secrets-sync-panel.tsx300줄 구현됨
이 패턴을 어댑터 패턴으로 범용화하면 Vercel/Railway/Netlify 확장이 가능합니다. 기존 인프라의 약 80%를 재활용할 수 있습니다.

아키텍처: 어댑터 패턴

src/lib/sync/ |-- types.ts # SyncAdapter 인터페이스 |-- trigger.ts # 범용 triggerAllSync |-- adapter-registry.ts # 어댑터 등록/조회 |-- name-map.ts # 플랫폼별 키 이름 매핑 |-- adapters/ |-- github.ts # 기존 auto-sync.ts 이동 |-- vercel.ts # Vercel REST API |-- railway.ts # Railway GraphQL API |-- netlify.ts # Netlify REST API

환경변수 CUD (생성/수정/삭제) | v triggerAllSync() | v project_sync_targets 조회 (auto_sync_enabled = true) | +---> [GitHub] auto-sync.ts ---> NaCl 암호화 ---> GitHub Secrets API | +---> [Vercel] vercel.ts ---> HTTPS TLS ---> Vercel Env API | +---> [Railway] railway.ts ---> HTTPS TLS ---> Railway GraphQL | +---> [Netlify] netlify.ts ---> HTTPS TLS ---> Netlify Env API | v last_sync_* 상태 기록 + logAudit()

DB: project_sync_targets 신규 테이블

CREATE TABLE project_sync_targets (
  id UUID PK,
  project_id FK -> projects(id),
  user_id FK -> auth.users(id),
  platform TEXT CHECK (IN ('github','vercel','railway','netlify')),
  service_account_id FK -> service_accounts(id),
  external_project_id TEXT NOT NULL,
  external_project_name TEXT,
  auto_sync_enabled BOOLEAN DEFAULT false,
  sync_environment TEXT DEFAULT 'production',   -- Linkmap 환경
  target_environment TEXT,                      -- 플랫폼 측 환경
  last_synced_at TIMESTAMPTZ,
  last_sync_status TEXT,
  last_sync_error TEXT,
  UNIQUE(project_id, platform, external_project_id, sync_environment)
);

UX 플로우 (바이브코더 기준)

  1. 프로젝트 설정 → "동기화" 탭
  2. "동기화 대상 추가" → 플랫폼 카드 선택 (Vercel / Railway / Netlify)
  3. 토큰 입력 (이미 서비스 연결되어 있으면 자동 감지)
  4. 플랫폼 프로젝트 선택 (API로 목록 조회 → 드롭다운)
  5. 환경 매핑 (Linkmap production → Vercel production)
  6. "자동 동기화" 토글 ON
  7. 이후 환경변수 변경 시 자동 push

6. 기각된 원안 & 보류 대안

기각: 런타임 중계 (Pull)

SDK 필요, SPOF 위험, "키의 키" 문제, 경쟁 우위 부재로 기각. 상세 분석은 위 섹션 3~4 참조.

보류: 보안 강화 (per-project 암호화, 토큰 스코프, MFA)

Push 기능과 독립적으로 진행 가능. 별도 스프린트로 검토 예정.

보류: CLI pull 강화 (CI/CD 빌드 시점 주입)

이미 80% 구현됨. Push 동기화와 병행 가능.
