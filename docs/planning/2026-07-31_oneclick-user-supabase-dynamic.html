1결론 요약

기술적으로 가능한가?

가능 — GitHub Pages 정적 export 모델을 그대로 유지한 채 가능 (supabase-js CSR + anon key + RLS).

수동 과정을 없앨 수 있는가?

가능 — 기본값은 관리형 위젯(1클릭), "내 DB로 승격"은 OAuth 완전 자동(복붙 0회). 수동 SQL 복붙은 폴백으로만 존재.

심플함에 걸림돌인가?

아니오 (v2 설계 기준) — 사용자 최소 경험은 "위젯 켜기" 1클릭. 배포 위저드는 무변경.

방향성과 충돌하는가?

오히려 부합 — 관리형(1층, 즉시 가치) → 내 DB 승격(2층, 학습 이벤트)이 퍼널 그 자체.

핵심 원칙 (v2) — "위젯은 1클릭으로 즉시 작동(관리형), '내 Supabase로 승격'은 원할 때 자동으로(OAuth), 복붙은 어디에도 없다"

2기술 구조 — 왜 가능한가

현재 구조 (2026-07-31 코드 조사)
  • 템플릿 = Next.js 15 소스 번들 → 사용자 GitHub 레포 push → Actions 빌드(output: 'export') → GitHub Pages 정적 호스팅
  • 사용자 데이터는 전부 src/lib/config.ts에 빌드 타임 상수로 emit — 런타임 데이터 소스 없음, 외부 연동은 GA 스니펫뿐
  • GitHub 토큰은 service_accounts에 AES-256-GCM 암호화 저장 — 동일 패턴을 Supabase 토큰에 재사용 가능
[방문자 브라우저] GitHub Pages 정적 사이트 (지금과 100% 동일) │ └─ 동적 모듈 (방명록 · 문의폼 · RSVP) ├─ [관리형] fetch → Linkmap API (Workers) → Linkmap DB ← 기본값 └─ [승격 후] supabase-js → 사용자 개인 Supabase (anon key + RLS)

3수동 과정 제거 전략 (v2 핵심)

3.1 수동 연결의 마찰 해부 — 약 14단계

구간단계내용이탈 위험
Supabase 가입~5사이트 이동 · 가입 · 이메일 인증 · 로그인높음 외부 이탈 + 인증 대기
프로젝트 생성~4조직/이름/리전 선택 · DB 비밀번호 결정 · 프로비저닝 ~2분높음 리전·비밀번호는 초보에게 낯선 결정
테이블 생성~3SQL 복사 · SQL Editor 이동 · Run중간 SQL 자체가 공포 요소
키 입력~2URL·anon key 복사 → Linkmap 입력중간 service_role 오입력 사고 위험

원클릭 컨셉과 정면 충돌 → 아래 3개 전략으로 구간별 제거.

전략 A — Linkmap 관리형 위젯 기본값 · 진짜 1클릭
방명록 모듈 토글 ON→재배포 (자동)→끝 — 0/14단계
  • Supabase 계정·가입·복붙 전부 불필요. Linkmap DB에 위젯 테이블(deploy_id 스코프 + RLS) + 공개 위젯 API GET/POST /api/oneclick/widget/[deployId]/entries (해당 라우트만 CORS 개방)
  • config emit은 endpoint URL만 — 키 노출 자체가 없음
  • 스팸 통제가 오히려 강해짐 — 3안 중 유일하게 서버 경유라 Cloudflare Rate Limiting으로 통제 가능 (BYO 직결에선 불가능)
  • 플랜별 쿼터(엔트리·위젯 수)로 비용 통제 — quota.ts 패턴 재사용, 유료 전환 포인트
  • 트레이드오프: 데이터가 Linkmap에(→ 승격으로 해소, "언제든 가져가기"가 신뢰 포인트) · Workers 부하(리스크 §6-9) · 신규 마이그레이션
전략 B — Supabase OAuth 완전 자동 프로비저닝 "내 DB로 승격" · 복붙 0회
[내 Supabase로 승격]→GitHub로 가입/로그인→동의 1클릭→이하 전자동 + 진행바
#자동화 단계방법제거되는 수동
1가입/로그인OAuth 진입 시 Supabase가 처리 — GitHub 소셜 로그인 유도 (원클릭 사용자는 GitHub 보유 전제 → 이메일 인증 대기 없음)가입 5단계 → 클릭 1~2회
2동의OAuth2 authorize (Linkmap = Supabase OAuth App)—
3조직/프로젝트 확인GET /v1/organizations · GET /v1/projects — 기존 있으면 선택지, 없으면 신규조직 결정
4프로젝트 생성POST /v1/projects — 이름 자동(사이트명 기반) · 리전 자동(ap-northeast-2) · DB 비밀번호 자동 생성 + 1회 표시프로젝트 생성 4단계
5프로비저닝 대기~2분 폴링 — 기존 deploy-status.ts 폴링 UX 재사용대기 이탈 방지
6테이블+RLS 생성POST /v1/projects/{ref}/database/query → pg_policies로 활성 기계 검증SQL 복붙 3단계
7anon key 회수GET /v1/projects/{ref}/api-keys키 복붙 2단계
8데이터 이전관리형 엔트리 → 새 테이블 insert (건수 대조)—
9config emit → 재배포기존 batch-update 파이프라인 그대로—
10토큰 파기기본: 완료 즉시 파기. Health Check 동의 시에만 암호화 보관상시 강권한 회피

남는 수동은 "동의" 클릭뿐 — 계정 권한 위임이므로 제거가 불가능하고 제거해서도 안 되는 단계.

전략 C — 반자동 폴백 폴백 전용 · 기본 경로 아님
  • 대상: OAuth 거부/실패 사용자, 이미 자기 프로젝트를 쓰는 고급 사용자
  • SQL 복붙 → SQL Editor 프리필 딥링크(supabase.com/dashboard/project/_/sql/new, 공식 quickstart 패턴)로 "클릭 → Run 1클릭" 축소 (프리필 파라미터 사양은 구현 시 검증)
  • 키 입력 → anon key 위치 딥링크 안내 + service_role 오입력 감지·거부(prefix 검사) 필수
  • 14단계 → 약 6단계

3.5 전략 비교와 권장 조합

사용자 클릭복붙Supabase 계정스팸 통제데이터 소유구현 난이도
수동 (v1안, 폐기)~14단계3회필요불가사용자하
A 관리형 (기본)1클릭0회불필요강함 (CF rate limit)Linkmap (이전 가능)중
B OAuth 승격3~4클릭0회필요 (GitHub로 즉시)DB 제약만사용자중상
C 반자동 폴백~6단계1~2회필요DB 제약만사용자하
권장 조합 — A를 1층 기본값(원클릭 유지) + B를 "내 Supabase로 승격" 버튼(2층 학습 이벤트) + C는 B의 폴백.
수동 복붙은 어떤 기본 경로에도 등장하지 않는다.

4현재 방향성과의 차이

항목현재확장 후 (v2)
필요 외부 계정GitHub 1개GitHub 1개 (관리형) / +Supabase (승격 선택 시)
사이트 성격순수 정적정적 + 동적 위젯 (방명록·문의·RSVP)
데이터 위치레포 config.ts+ Linkmap DB(관리형) 또는 사용자 DB(승격)
반영 속도편집 → 재빌드 수 분동적 데이터는 즉시
위젯 활성화 비용—1클릭 (모듈 토글)

퍼널 관점 — 관리형→승격 구조가 코어 컨셉("배우다 보니 관리가 되어 있는")과 정확히 일치. 1층에서 마찰 0으로 방명록이 작동하고, "내 DB로 가져가기"가 바이브코더의 첫 자발적 인프라 학습 이벤트가 된다. 승격 시 서비스맵 노드·환경변수·Health Check 자연 활성화.

온보딩 마찰 — 기본 경로에서 Supabase 가입이 완전히 사라져 1층 진입률 영향 없음. 배포 위저드(3단계)는 여전히 무변경.

5사전작업

보안 선결 (P0 — 이 기능 이전에 반드시)
  • OAuth 콜백 크로스계정 CSRF 수정 (07-12 감사 P0, 미수정) — Supabase provider가 같은 콜백을 타므로 수정 없이는 공격 표면 확대
  • GitHub Secrets 경로 nacl 논스 버그 — 본 기획은 anon key 평문 emit + endpoint emit이라 Secrets 경로 회피 가능
전략 A (관리형) 사전작업
  • 위젯 데이터 테이블 마이그레이션 (RLS + 정책 + created_at + deploy_id FK) + 플랜별 쿼터 (quota.ts 패턴)
  • 공개 위젯 API (5단계 규칙, 익명 POST는 Zod + honeypot + 글자수 제한) + 해당 라우트만 CORS 개방
  • Cloudflare Rate Limiting Rule 추가 (앱 코드 아님 — 기존 정책 준수)
  • 동적 모듈 1종: invitation 방명록/RSVP — 스키마·제너레이터·프리뷰 3중 구조 + module-roundtrip.test.ts 확장
전략 B (OAuth 승격) 사전작업
  • Supabase 조직 설정에서 OAuth App 등록 (redirect URI · 스코프)
  • service_accounts에 supabase provider 추가 (AES-256-GCM 재사용) + 사용 후 파기 플로우
  • RLS 표준 SQL 템플릿 — 방명록: 공개 read + 익명 insert / 문의폼: insert만·read owner 한정(공개 read 금지) / RSVP: insert + 확인 코드 조회 — pg_policies 기계 검증
  • 프로비저닝 폴링 UX (deploy-status 패턴 재사용) · 관리형→승격 데이터 이전 로직
  • supabase-js 고정 버전 + lockfile 규칙 (npm view 검증), 또는 CDN 방식 검토

6고려사항 / 리스크

리스크수준대응
RLS 없는 테이블 + anon key = DB 전체 공개높음RLS 포함 SQL만 자동 실행 + pg_policies 기계 검증. 임의 테이블 연결 기능 없음
Management API 토큰 = 계정 전체 제어 권한높음 (B)기본: 프로비저닝 완료 즉시 파기. Health Check 동의 시에만 암호화 보관
익명 insert 스팸중간관리형: CF rate limit (강함) / 승격 후: 글자수·honeypot·DB 제약. Edge Function은 비목표
무료 티어 프로젝트 자동 일시정지 → 위젯 깨짐중간위젯 우아한 실패(섹션 숨김) + Health Check 감지·알림 (2층 셀링 포인트)
무료 조직 활성 프로젝트 2개 제한중간 (B)프로비저닝 전 GET /v1/projects 확인 → 기존 프로젝트 선택지 제시 · 한도 초과 안내
DB 비밀번호 자동 생성의 전달 문제중간 (B)생성 직후 1회 표시 + "대시보드에서 재설정 가능" 안내. Linkmap은 저장하지 않음
사용자가 자기 DB에서 테이블 삭제·변경중간조용한 폴백 + "연결 재설정"(재프로비저닝) 버튼 — OAuth 재동의로 원클릭 복구
기존 편집·재배포 P1 결함 위 적층중간편집 경로 P1(멀티계정 토큰 오참조 등) 선정리 권장
관리형 위젯 API의 Workers 부하 (Free plan 503 이력)중간 (A)위젯 라우트 경량화 + GET 캐싱 + rate limit + 쿼터. cpu_ms 설정 확인
관리형→승격 데이터 이전 무결성낮음이전 후 건수 대조 · 원본 soft 보관 후 지연 삭제
문의폼 개인정보 책임 경계낮음관리형: 보관정책 명시 / 승격 후: 사용자 소유·사용자 DB 명시

7단계별 로드맵 (v2, 검증 기준 포함)

Phase 0
보안 선결OAuth 콜백 P0 수정 + 편집 경로 P1 정리
감사 항목 재현 테스트 통과
Phase 1
관리형 위젯 (전략 A)invitation 방명록/RSVP 모듈 + Linkmap 위젯 API + 쿼터 + CF rate limit

Phase 2

각 Phase는 독립 출시 가능. Phase 1만으로 "원클릭 동적 위젯"이라는 사용자 가치가 완성되고, Phase 2부터 소유권·학습 가치가 추가된다.

8비목표 (이번 범위에서 하지 않는 것)

  • 배포 위저드(3단계) 변경 — 위젯은 편집기(배포 후) 진입점에서만
  • 수동 SQL 복붙을 기본 경로에 두는 것 (폴백으로만 존재)
  • 사용자 Supabase에 Edge Function/서버 코드 배포
  • 임의 테이블 연결 기능 — RLS 통제 불가
  • 호스팅형(/s/[slug]) 발행 모델 전환 — 별도 설계 트랙(2026-06-18) 유지
  • 사용자 사이트 자체의 회원제/로그인 — 복잡도 급증, 추후 별도 검토
