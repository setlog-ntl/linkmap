병렬 개발 충돌 방지 전략

여러 Claude Code 세션을 동시에 돌릴 때 커밋 충돌 없이 작업하는 방법
2026-04-03 | Linkmap Planning Document

1. 문제 진단: 왜 롤백이 발생하는가?

핵심 원인: 같은 브랜치에서 여러 세션이 동시 커밋

여러 Claude Code 세션이 같은 main 브랜치에서 작업하면, 각 세션은 자신이 읽은 시점의 파일 상태를 기준으로 수정합니다. 세션 A가 커밋한 후 세션 B가 같은 파일을 수정하면, B는 A의 변경사항을 모르는 상태에서 커밋하므로 A의 작업이 사실상 덮어써집니다.

시간축 → 세션 A (블로그) 파일 읽음 ──── 수정 중 ──── 커밋 A ───────────────── 세션 B (서비스맵) 파일 읽음 ──────────── 수정 중 ──── 커밋 B (A 덮어씀) 공유 파일 예시: - src/data/seed/*.ts (여러 기능이 참조) - src/types/*.ts (타입 정의 공유) - src/lib/queries/keys.ts (쿼리키 팩토리) - src/components/layout/* (레이아웃 컴포넌트) 특히 위험한 패턴: - barrel export (index.ts) 수정 충돌 - 같은 시드 파일에 서로 다른 데이터 추가 - 공통 유틸 함수 변경
현재 우회 방법: 서로 완전히 다른 영역(예: 블로그 vs 서비스맵)을 작업하여 파일 겹침을 방지. 이 방법은 작동하지만, 프로젝트가 복잡해질수록 "완전히 다른 영역"을 보장하기 어려워집니다. 특히 types, lib, data 폴더의 공유 파일이 예상치 못하게 겹칠 수 있습니다.

2. 해결 옵션 비교

A 현행 유지 — 영역 분리 + 주의

지금처럼 각 세션이 완전히 다른 영역을 작업하고, 공유 파일 수정을 피하는 방식을 계속 유지합니다.

변경 없음 즉시 적용
생산성
7/10
안전성
5/10
확장성
3/10

장점

  • 지금 바로 사용 가능
  • 추가 학습/설정 없음
  • 간단한 작업에 충분

단점

  • 공유 파일 수정 시 충돌 위험 상존
  • 기능이 복잡해질수록 "다른 영역" 보장 어려움
  • 수동으로 영역 관리하는 인지 부하
  • 실수 시 롤백/충돌 해결 시간 소모
B 경량 워크트리 — 기존 /wt 스킬 활용 (PR 없이)

이미 구현된 /wt-new로 워크트리를 만들되, PR 생성 없이 직접 main에 머지하는 간소화 버전. 브랜치 격리의 안전성 + 바이브코딩의 속도를 동시에 확보합니다.

이미 도구 있음 워크플로우만 변경 PR 생략 가능

간소화된 워크플로우

Step 1: 워크트리 생성

/wt-new "블로그 시리즈 추가" → 자동으로 별도 폴더 + 브랜치 생성

Step 2: 작업 + 커밋

해당 워크트리에서 자유롭게 작업. 다른 세션과 완전히 격리됨

Step 3: 머지 (PR 생략)

/wt-done 또는 새 /wt-merge 커맨드 → main으로 직접 머지 + 충돌 시 즉시 알림

Step 4: 자동 정리

워크트리 삭제 + 브랜치 삭제. 깨끗한 상태로 복귀

장점

  • 각 세션이 물리적으로 격리 (파일 겹침 불가)
  • 충돌 시 머지 단계에서 명확히 감지
  • PR 없이도 안전한 병렬 작업
  • 이미 /wt-new 도구가 구현되어 있음
  • 기존 작업 방식에서 커맨드 1개만 추가

단점

  • 워크트리당 npm install 시간 (초기 1회)
  • 디스크 공간 약간 추가 사용
  • 머지 시 충돌 해결이 필요할 수 있음
C 자동 동기화 훅 — 커밋 전 자동 pull + rebase

Claude Code 훅(hook)으로 커밋 전에 자동으로 git pull --rebase를 실행하여 다른 세션의 변경사항을 먼저 반영한 뒤 커밋합니다.

훅 설정 필요 main 직접 작업
생산성
8/10
안전성
6/10
확장성
5/10

장점

  • 기존 워크플로우 거의 변경 없음
  • main에서 직접 작업 가능
  • 단순 충돌은 자동 해결

단점

  • rebase 충돌 시 세션이 멈춤
  • 같은 파일 수정 시 여전히 수동 해결 필요
  • rebase 중 워킹 디렉토리 오염 가능
  • 근본적 해결이 아닌 증상 완화
D 세션 락 — 작업 영역 선언 + 파일 잠금

각 세션이 시작할 때 작업할 파일/폴더를 선언하고, 다른 세션이 해당 파일을 수정하지 못하도록 소프트 락을 거는 방식입니다.

커스텀 구현 필요 복잡도 높음
생산성

안전성
9/10
확장성

장점

  • 파일 수준에서 충돌 원천 차단
  • 어떤 세션이 어떤 파일을 쓰는지 명확

단점

  • 락 관리 시스템 직접 구현해야 함
  • 세션이 비정상 종료 시 락 해제 문제
  • 예상 못한 파일 의존성 처리 어려움
  • 바이브코딩과 정반대의 무거운 프로세스

4. 추천안: B + A 혼합 전략

핵심 제안: 작업 규모에 따라 A(현행)와 B(워크트리)를 유연하게 혼합합니다. 큰 기능은 워크트리로, 작은 수정은 main에서 직접. PR은 완전 생략.

상황별 워크플로우 가이드

작업 유형 방법 이유
타이포 수정, CSS 미세조정 main 직접 충돌 가능성 거의 없음
1개 파일 내 수정 main 직접 다른 세션과 겹칠 확률 낮음
새 블로그 포스트 추가 워크트리 posts-meta.ts, content-map.ts 등 공유 파일 수정
새 서비스 추가/수정 워크트리 seed 파일, 타입, 쿼리 등 여러 파일 연쇄 수정
컴포넌트 리팩토링 워크트리 import 변경이 다른 파일에 영향
DB 마이그레이션 포함 작업 워크트리 필수 types + queries + schema 동시 변경

필요한 구현: /wt-merge 커맨드 (PR 없는 빠른 머지)

기존 /wt-done에서 PR/CI 단계를 제거한 경량 버전:

/wt-merge 워크플로우: 1. 현재 워크트리의 변경사항 커밋 확인 2. main 브랜치 최신 상태로 pull 3. main에 머지 (--no-ff 또는 squash 선택) 4. 충돌 발생 시: 충돌 파일 목록 표시 + 해결 안내 5. 성공 시: 워크트리 삭제 + 브랜치 삭제 + main 복귀 소요 시간: ~10초 (PR+CI 대비 5분+ 절약)

5. 현행(A) 유지 시 알아야 할 것들

현재 방식도 괜찮은 경우

  • 동시 세션이 2개 이하이고, 작업 영역이 명확히 다를 때
  • 공유 파일(types, lib, data)을 동시에 수정하지 않을 때
  • 각 세션의 작업이 30분 이내로 짧을 때 (겹칠 시간이 적음)

위험해지는 시점

  • 3개 이상 세션을 동시 운영하기 시작할 때
  • 새 서비스/블로그/기능 추가처럼 여러 파일을 건드리는 작업이 겹칠 때
  • src/types/, src/data/seed/, src/lib/queries/ 같은 허브 파일을 두 세션이 동시에 수정할 때
  • 작업 시간이 길어져서 다른 세션의 커밋을 모르고 작업하는 시간이 늘어날 때
솔직한 평가: 현재 방식은 "조심하면 괜찮다"입니다. 문제는 바이브코딩의 핵심 가치가 "조심하지 않아도 되는 것"이라는 점입니다. 워크트리는 "조심하지 않아도 안전한" 환경을 제공합니다.

6. 의사결정 가이드

아래 질문에 답하면 최적 전략이 결정됩니다

Q1. 동시에 몇 개 세션을 운영하나요?
1~2개: A(현행)로 충분
3개+: B(워크트리) 강력 추천
Q2. 공유 파일(types, seed, queries)을 동시에 수정하는 경우가 있나요?
거의 없음: A로 충분
가끔 있음: B 추천
자주 있음: B 필수
Q3. 워크트리 생성 시 npm install (~30초) 대기가 괜찮은가요?
괜찮음: B 적합
싫음: A + 조심 or C(자동 동기화)
Q4. PR/CI 프로세스를 유지하고 싶은가요?
필요 없음: B의 /wt-merge (PR 생략) 사용
중요 기능만: B의 /wt-done (PR+CI) 선택적 사용
항상 필요: 기존 /wt-done 유지
Q5. 롤백 사고가 얼마나 자주 발생하나요?
월 1회 미만: A로 충분, 사고 시 수동 복구
주 1회+: B로 전환하여 원천 차단
